## 结论：当前 CI 不可信，而且它不是门禁，只是提交后的通知

一句话：**它只能证明“文本行数没超”，不能证明“代码能编译、测试能过、产物能跑”；并且它连“拦住合并”都做不到。**

| 层 | 判断 | 依据 |
|---|---|---|
| 是否阻塞合并 | **否** | `branches/main/protection` → 404 `Branch not protected`；`rulesets` → `[]`；仓库没有任何 PR（`pulls?state=all` 长度 0），全部直接 push main |
| 是否验证真实风险 | **否** | `ci.yml` 只有 `code-size` 一个 job，跑 `bash tools/check-code-size.sh`，实测 6 秒；不装 Qt、不编译、不跑测试、不执行产物 |
| 这个检查是否可信 | **作为 lint 可以，作为 gate 不行** | 结果确定、无 flaky；但阈值由当前代码生成，`--update-baseline` 可自批，检查范围由被检查者定义 |

## 一、当前 `code-size` gate 的漏洞

脚本实现本身比大多数 CI 脚本认真（参数校验、baseline 格式校验、stale 提示、退出码）。
问题在**它证明的东西和它声称的职责不匹配**。

**1. 同一提交可以既改代码又改阈值。** `--update-baseline`（`check-code-size.sh:168-223`）
按当前行数重写 baseline，“抬高”只打印一行提示，不失败、不审批。CI 只在事后对这个提交
跑 `check`，所以“文件 +600 行 + 重新生成 baseline”一个 commit 就能全绿。
更何况有先例：`329b2dd` 提交信息是 `ci: tighten the code-size baseline after the test split`，
diff 里却有

```text
-src/next/app/NextWindow.cpp	4014
+src/next/app/NextWindow.cpp	4022
```

“收紧”的提交把上限抬高了 8 行。**只要改数字和改代码在同一个 PR，ratchet 就退化成注释。**

**2. 阈值由当前代码定义。** `01297ea` 首次生成时阈值 2500 行；`fd14c1d` 改成 1500 并登记 17 项；
今天剩 13 项，数字与当前 `wc -l` 逐个相等（3143、2346、2250……1524）。“允许的上限”=“此刻的行数”。
最典型的后果是 `src/render2/Render.cpp`：现在 **1499 行**，历史 `1273→1354→1469→1485→1490→1492→1499`，
且没有 baseline 条目——下一次动它一行就必红，而“修绿”的最短路径是把它加进 baseline。
**这个 gate 最终一定会为它本该防的那个文件发一张豁免证。**

**3. 13 条 baseline 全是测试文件。** 全部位于 `src/**/tests/`。生产代码最大 1499 行，没有 ratchet
保护；真正被卡住的是测试文件——而测试文件大通常意味着“难维护”，不是“模块太胖”。
把逻辑在生产/测试之间挪动会得到与“拆分模块”相反的激励。

**4. 检查范围由脚本自己划。** `collect_sizes()` 只匹配 `src/` 下 `*.cpp`/`*.h`：
新增 `*.hpp`、`*.cc`、`*.cxx`、`*.inc`、`*.ipp` 完全不计；`#include "big_impl.inc"` 不计；
源码放到 `src/` 之外（CMake 完全可以）不计；`-not -path '*/build/*'` 也不排除 `src/generated/`。
等于自己划考试范围。

**5. `main.cpp ≤ 300` 是路径规则。** 改名为 `src/app/entry.cpp` 并改 `CMakeLists.txt:204` 的
`add_executable(pvforge src/main.cpp)`，硬规则就消失，只剩 1500 行通用上限。当前 128/300，
留了 2.3 倍空间，也没有任何检查验证“入口只做装配”。

**6. 没有总量预算。** 拆成两个 1490 行文件即合规，总行数可无限涨；`wc -l` 对单行 50KB 的巨型表达式无感。
它衡量的是文件边界，不是复杂度。

**小结**：这是一个可用的 lint，问题是被人当成 CI 的全部，并在 README 里描述成“阻塞合并”。
该修的是定位和门禁，不是继续给它加规则。

## 二、历史 CI 的自我欺骗证据

**证据 1：同一个失败，一次绿一次红，判决靠运气。** `--repeat until-pass:2` 让同类 flaky 在不同提交上得到相反判决。

- run `43327537969`，job `131563688576`（Qt 6.6.3 debug，2026-11-12T23:20Z）：
  `html2.renderFrameColors`、`html2.frameCacheHits` 首跑失败，重试通过，
  `100% tests passed, 0 tests failed out of 338`，**run 绿**。
- run `43331676958`，job `131577644382`（纯 docs 提交，23:52Z）：同类 Chrome/CDP 失败
  （`Browser.getVersion timed out`），`html2.renderFrameColors` 两次都失败，
  `99% tests passed, 1 tests failed out of 344`，**run 红**。

一个 docs-only 提交让 CI 变红，说明红绿与代码改动无关；重试只是把骰子多掷了一次。
真正修好它的是 `bdf81a0c`（`RESOURCE_LOCK pvforge_chrome`，序列化 Chrome 用例）——
红 run 之后 6 分钟就出现了。**问题本来就能修，不需要重试。**

```bash
gh api repos/xmb505/pvforge/actions/jobs/131563688576/logs | grep -aE "Test #18[0-9]|tests passed"
gh api repos/xmb505/pvforge/actions/jobs/131577644382/logs | grep -aE "Test #18[0-9]|tests passed"
```

**证据 2：`KNOWN_FLAKY` 白名单指错对象。** `1ecc1d5` 第一版矩阵就带着
`(viewport\.tests|next\.media_services|next\.camera_monitor)` —— **在任何 CI 数据之前**就写死。
而 11-12 17:00–23:00 所有 debug job 里这 3 个用例每次都是 `0 tests failed out of 3`；
同期真正失败的是 `html2.*` 和 `next.workbench_integration`（run `43265321339` job `131347212076`
首跑失败、重试通过），都不在名单里。整组排除的代价是这 3 个用例永久失去判决，
排除理由（“参考壳 flaky”）随参考壳删除而失效，名单却一直留到 CI 被删。

**证据 3：advisory 数字 gate 上线 13 分钟就改成不阻塞。** `9deb085`（07:04）新增 `doc-metrics`，
注释写“不一致就判红”；`59b1d1b`（07:17）加 `continue-on-error: true` 并改名“（advisory）”。
之后 run `43334873257` 里 doc job **conclusion = failure**（“`src/tests` 行数 文档 25279 ≠ 实际 25252”），
整个 run **conclusion = success**；同样的“job 红、run 绿”还有 `43334575735`、`43334711434`。
完整生命周期：加上 → 发现它会红 → 改成不阻塞 → 留着当装饰。

**证据 4：取消被当成通过。** `cancel-in-progress: true` 在 main 上意味着“新 push 杀掉旧 run”。
11 个被取消的提交全部进了 main：`58424cf9`、`d0a6a2ae`、`26ca91e0`、`665cdf9c`、`1ae98d41`、
`a46baef4`、`4f5972f1`、`438c38c2`、`d25039a8`、`bdfeb805`、`75951394`。
其中 `75951394` 是“修 Qt 6.6 编译错误”的提交——**它自己没被 CI 验证过就合并了**；
三个 CI 自身的改动（`4f5972f1`、`438c38c2`、`d25039a8`）也被取消，等于写 CI 的人没验完就收工。

**证据 5：release 产物从来没被执行过。** 旧 Release leg 只有 `actions/upload-artifact`，
没有 `--version`、`ldd`、启动冒烟。`dist/RUN.txt:24` 的“ldd 已检查：均无 not found”是人工结果。
产物依赖系统 Qt ≥ 6.5 与 FFmpeg 运行库（`libavformat.so.62`），在 Ubuntu 24.04 默认 Qt 6.4.2 上
起不来——**CI 对此完全无感**。

**证据 6：有价值的红 run 都指向依赖/环境差异。** `43258648362`、`43259215122`、`43259959231`
（FFmpeg 6 与 8 API 差异，连续 3 个提交编译失败）、`75951394`（Qt 6.6 `QString::arg` 歧义）、
`43262365164`（缺 Qt WebP imageformat 插件，6 个用例失败）、`43331676958`（Chrome CDP 并行饥饿）。
这证明构建矩阵有价值，也证明成本很低：最后一次全量 CI 最慢 job 4m17s。

## 三、最小可信 CI（从真实失败模式反推）

### 阶段 0：本地 gate（今天就能做，0 CI 成本）

main 无保护、无 PR，**本地脚本是唯一真正能拦住东西的 gate**。

- 新增 `ci/verify.sh`，就是未来 CI 会跑的同一串命令，禁止两套逻辑；
- 顺序固定：干净 Release 构建 → 干净 Debug 构建 → 全量 `ctest` → 产物冒烟；
- `git config core.hooksPath .githooks` + `pre-push` 调用它（或人类手动跑）；
- 纪律写进 `ci/README.md`：**不通过不许 push main**。这是流程，但当前只有它能强制。

### 阶段 1：CI 第一条可信流水线（1 个 job，实测约 6–8 分钟）

只证明三件事：这棵树能编译、测试能过、产物能启动。

```text
ubuntu-24.04 + Qt 6.6.3（最低声明版本）+ runner 自带 FFmpeg
1  ci/install-deps.sh
2  cmake --preset debug && cmake --build --preset debug -j4
3  ctest --preset debug -j4 --no-tests=error --output-on-failure
4  cmake --preset release && cmake --build --preset release -j4
5  ./build/release/pvforge-mcp --version                 # exit 0
6  ! ldd build/release/pvforge | grep -q "not found"
7  QT_QPA_PLATFORM=offscreen timeout 15 ./build/release/pvforge
   # 期望 124（活到超时）；0 / 139 都算失败
8  断言 ctest 用例数 == ci/expected-tests.txt
```

要点：**不写** `--repeat`、`--exclude-regex`、`continue-on-error`、`|| true`；
用例数写进 `ci/expected-tests.txt`，删测试必须显式改它，评审能看到；
step 5/7 跑的必须是那个将被上传的二进制。若 `pvforge` 没有无头模式，就给 `src/main.cpp`
加一个 release 也编进去的 `--version`（照抄 `src/mcp/main.cpp:156-160`），这是为了让产物可验证。

### 阶段 2：补版本边界（约 10 分钟）

- 只给 **debug** 加 Qt 6.7.3 leg（6.6 的 `QString::arg` 歧义只有 6.6 才炸，最低版本 leg 不能省）；
- Release leg 只保留一个，不要 4 倍矩阵；
- 声明支持 FFmpeg 6 和 8 就必须各构建一次，只测 8 等于没测 6。

### 阶段 3：让 gate 变成 gate

1. main 开 branch protection，required checks 包含 CI 的 job 名；
2. `ci.yml`、`check-code-size.sh`、baseline 的改动必须单独 PR，且附一次“故意弄红”的运行证据
   （临时分支注入编译错误 / 必失败测试，贴 run id）；
3. baseline diff 由 CI 校验：只允许删除或减小；新增/抬高必须同时写拆分计划，否则拒绝；
4. `concurrency` 不能抹掉判决：用 merge queue，或对每个 push 的 tip 保留一次完整 run。

### `code-size` 去留

保留但降级为普通 lint：不能是唯一 job，不能再写“阻塞合并”；baseline 改动与源码分离并校验单调性；
检查范围改读 `compile_commands.json` 或 CMake target 源文件列表，避免换后缀绕过。

## 五、独立审查 checklist（Agent A 写 CI，Agent B 逐条打回）

Agent B 只看 diff + 运行记录 + 代码，不看作者解释。每条给“通过/打回”，打回必须写证据。

**A. 门禁是否真的是门禁（P0）**
- [ ] A1 branch protection 有 required status checks 且包含本次 job；否则不许写“阻塞合并”。
- [ ] A2 仓库有 PR 流程吗？全直接 push main 时，`pull_request` 触发等于从未执行，必须指出。
- [ ] A3 `concurrency` 不会让 main 的提交失去判决；`cancel-in-progress: true` 必须说明补偿机制。
- [ ] A4 `ci.yml` 改动有运行记录，且 run 的 commit 就是被评审的 commit。

**B. 是否覆盖真实失败模式（P0）**
- [ ] B1 至少一个“编译 + 运行测试”的 job；只有文本统计 → 打回。
- [ ] B2 至少一个 Release 构建，并**执行**了产物（version / 启动 / ldd），不是只上传。
- [ ] B3 干净环境从零 configure，不依赖仓库内 build 目录；ccache 允许，cache miss 不影响判决。
- [ ] B4 声明的 Qt/FFmpeg 多版本必须覆盖最低版本；删 leg 必须同 PR 改文档。
- [ ] B5 `ctest` 带 `--no-tests=error` 并断言用例总数；删测试必须显式改数字。
- [ ] B6 外部依赖（Chrome、ffmpeg、git）预装 + preflight，skip 数 > 0 视为失败，除非带 `SKIP_OK` 标签 + issue。

**C. 是否有“先射箭再画靶子”的痕迹（P0）**
- [ ] C1 grep `continue-on-error`、`--repeat`、`--rerun-failed`、`--exclude-regex`、`|| true`、`set +e`；出现即打回，例外须附 issue + 到期日。
- [ ] C2 没有 advisory 数字 gate；保留行数/doc 检查时，它不能出现在“质量门禁”叙述里。
- [ ] C3 阈值/baseline 改动与源码改动分离？同一 PR 同时改 → 打回。
- [ ] C4 baseline diff 单调不增？抬高 → 要求拆分计划，否则打回。
- [ ] C5 新 gate 是否证明过自己会红？要求临时分支制造失败并贴 run id；无负向证据 → 打回。
- [ ] C6 阈值是否等于“当前最大值”？是则必须给出外部依据。

**D. 失败后的行为是否诚实（P1）**
- [ ] D1 失败信息指向具体文件/用例，并给出“修代码”的路径，而不是“调阈值”。
- [ ] D2 每个测试有 `TIMEOUT`；超时按失败，不自动重试。
- [ ] D3 失败时上传可复现的日志/用例清单，不只是截图。
- [ ] D4 job 名、README 描述与实际一致（没做的别写“阻塞”“全量”“已验证”）。

**E. 成本与可维护性（P2）**
- [ ] E1 单次时长与历史基线（4–8 分钟）同量级；超 15 分钟须说明新增覆盖。
- [ ] E2 依赖安装不重复、不与 `ci/install-deps.sh` 漂移。
- [ ] E3 actions pin 到 SHA（检查 `actions/permissions` 的 `sha_pinning_required`）。
- [ ] E4 本地手动命令与 CI 命令不是两套。

```text
审查结论模板：
P0 打回：A1（无分支保护）、B1（只有文本统计）、C5（无负向证据）
P1 打回：D2（无 TIMEOUT）
通过：B3、B5、E2
结论：不可信，不得合并
```

## 六、给人类的三句话

1. **当前 CI 是绿的，但它绿的原因是它什么都不做。** 30 个代码提交、0 次编译，6 秒文本统计不构成验证。
2. **最狠的三个漏洞**：① 无分支保护/无 PR，任何 gate 都只是通知；② baseline 与源码同 PR 可改，历史上“收紧”提交还抬高了数字；③ 唯一检查衡量文件边界，与“能否编译、测试过不过、产物跑不跑”无关。
3. **最小可信 gate 三条**：干净环境 Debug 构建 + 全量 ctest（无重试/无排除/断言用例数）；Release 构建后**执行**产物（`pvforge-mcp --version`、`ldd` 无 not found、offscreen 启动存活）；main 开 required checks，CI/baseline 改动单独 PR 并附“故意弄红”的运行证据。
