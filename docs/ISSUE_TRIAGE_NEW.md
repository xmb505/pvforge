# 新模型风险清单（现有 issue 未覆盖）

> 对照范围：新实体模型设计、实现合同、全部 33 个 open issue。
>
> 现有 issue 绝大多数针对旧的 clip / 场景 / 文件夹模型。新模型重写后，其中不少问题被设计直接消除（例如视频默认时长、源帧偏移、父子范围、场景读写、退休容器）。本文只列**新模型自身仍然缺少规则**的地方，已覆盖的不重复提，对照表见文末。
>
> 结论：共 **52 条**风险，其中 P0 6 条、P1 39 条、P2 7 条。最危险的不是单个算法，而是三类“状态机缺口”：
>
> 1. 求解段只在“正常播放”路径上写了规则，裁剪、结束、组合、失败路径大片空白；
> 2. 引用关系（公转目标、父子关系）没有统一的环检测和悬空处理；
> 3. MCP 与人类共享同一份工程和 git 历史，却没有并发与操作者隔离。

## A. 求解段

### A1. 裁剪片段开头压到物理段上，整段物理消失且物体会瞬移

- **现象/触发**：把片段 start 向右裁，裁进重力/公转/黑洞段时，设计规定删掉该段的开始/结束标记，整段失效；同时裁剪又会删掉新 start 之前的关键帧，包括这段“带值的开始帧”。剩下的 x/y 轨道在新 start 处没有值，物体会跳到默认 0 或更早的关键帧。
- **期望**：裁剪压到段内时，应从裁剪点当前解算位姿继续；或者至少明确提示“会删除整段物理”并要求确认。不能留下没有初始值的驱动轨道。
- **影响**：用户只想修片头，结果整段动画消失、构图错位；AI 也无法从结果反推原因。
- **对应设计**：§5.4 求解关键帧 / 裁剪 start；§5.1 裁剪规则。
- **优先级**：P0
- **重复**：无。现有 #31 是普通 clip 裁剪不级联，不涉及求解段。

### A2. 物理段播完后接普通关键帧，画面会跳一下

- **现象/触发**：结束帧只是停止标记，不存值；解算到结束帧后的位姿只存在于运行时，没有写回轨道。设计又明确“不把求解轨迹烘焙成普通关键帧”。用户在结束帧之后加普通关键帧时，求值器不知道从哪个值开始插值，结束帧与下一个关键帧之间就会出现跳变。
- **期望**：提供“把结束位姿落成关键帧”的操作，或在模型里定义“段后保持值”作为插值起点；至少要能读到结束帧的精确位姿。
- **影响**：任何“先物理下落、再手动接动画”的工作流都做不顺；用户只能靠目测补一个近似值。
- **对应设计**：§5.4 结束帧 / 值保持；§10 明确不做“烘焙成普通关键帧”。
- **优先级**：P0
- **重复**：无。

### A3. 裁剪片段开头在物理段之前时，物理段会错位

- **现象/触发**：设计只写了“裁剪 start 切进求解段”和“移动实体时求解段随实体平移”，没有写裁剪 start 落在求解段**之前**时，段的相对帧号要不要跟着平移。JSON 示例和接口约定又暗示段帧号是相对实体 start 的，两种理解互相矛盾。
- **期望**：明确求解段帧号是全局帧还是相对实体 start；裁剪 start 在段之前时，按同一基准平移段的 start/end，并保持解算参数不变。
- **影响**：实现一旦选错基准，裁剪后物理段会在错误的时间开始，驱动轨道锁错区间，预览和导出对不上。
- **对应设计**：§5.4 求解段起止 / 移动实体；§5.1 裁剪 start。
- **优先级**：P0
- **重复**：无。

### A4. 物理段内还能写进普通关键帧，出现两套互相打架的动画

- **现象/触发**：设计只说“段内不能给被驱动属性加普通关键帧”，但没有规定创建求解段时如何处理区间里**已经存在**的关键帧，也没有说 `keyframes.set`、`keyframes.setMany`、`keyframes.move`、`entity.update` 写轨道、裁剪把关键帧平移进段内、undo 恢复旧关键帧这些入口要怎么拦。
- **期望**：所有写入路径统一校验；创建段时先列出冲突关键帧，要求删除或移动；越界写入返回允许范围和原因，而不是静默接受。
- **影响**：同一属性同时有普通关键帧和求解器两个真相，播放结果取决于求值顺序；用户看到的关键帧和实际运动对不上。
- **对应设计**：§5.4 段内限制；§5.3 关键帧写入工具。
- **优先级**：P1
- **重复**：相关 #18、#33（关键帧越界/小数帧校验），但本条是“段内驱动属性与普通关键帧的双重真相”，未被覆盖。

### A5. 没有结束帧的物理段会堵死后面的段，拉长片段还会让它无限延长

- **现象/触发**：没有结束帧时段一直解到片段最后一帧。因为段不能重叠，后面再创建任何段都会和它冲突。另一种情况：裁剪 end 切进段会移除结束标记，段跑到新末帧；之后再把片段拉长，这个段又会跟着长，物理永远停不下来。
- **期望**：只有最后一个段允许省略结束帧；裁剪 end 切进段时写入一个被截断的结束标记，或记录“曾被截断”，之后拉长片段不自动恢复物理。
- **影响**：AI 按“先建一段、再建下一段”的顺序会直接撞校验；用户拉长片段后运动范围悄悄变了。
- **对应设计**：§5.4 无结束帧 / 裁剪 end；§3.4 扩大范围不恢复已删除内容。
- **优先级**：P1
- **重复**：无。

### A6. 删掉公转/黑洞目标后，物理段变成悬空引用

- **现象/触发**：公转和黑洞的 `targetUuid` 可以指向任意实体，不要求是子级。删除目标实体只级联删除它的后代，不会清理其他实体里指向它的求解段；换父级还会改变目标的坐标系。
- **期望**：删除/换父级前返回依赖列表；要么阻止，要么把受影响的段转成“目标缺失”错误态并在 UI/MCP 明确显示；打开工程时校验悬空引用。
- **影响**：预览解算找不到目标，可能无解、NaN 或崩溃；工程表面正常，播放到该段才坏。
- **对应设计**：§5.4 公转/黑洞目标；§3.4 删除级联。
- **优先级**：P1
- **重复**：无。

### A7. 物理参数写错名字也能成功，动画静默用默认值

- **现象/触发**：`solver.create` 的 `params` 是无类型键值表，参数单位、默认值、合法范围都留到“待细化”。AI 把 `strength` 写成 `gravity`、把 `periodFrames` 写成 `period`，工具仍返回成功，解算器读不到就用默认值。
- **期望**：每种效果有独立 schema；未知参数直接报错；`solver.evaluate` 返回实际生效的参数和单位，AI 能自查。
- **影响**：和旧模型“写 clipStart 静默无效”同类：返回成功但画面不动，排查成本极高。
- **对应设计**：§5.4 参数；§11 待细化。
- **优先级**：P1
- **重复**：现象同类于 #32（写音频范围静默无效），但求解参数未被任何 issue 覆盖。

### A8. 长工程拖播放头/导出会越来越卡，预览和导出还可能不一致

- **现象/触发**：固定步长从段起点逐帧积分；拖到第 5000 帧要算 5000 步，每步还要扫描所有可碰撞实体。预览如果为了跟手跳帧，导出却逐帧算，缓存键又没有定义（段版本、参数、fps、起始帧是否参与）。
- **期望**：按段缓存/检查点，支持增量前进和任意帧确定性求值；预览与导出共用同一份缓存语义；提供进度和取消。
- **影响**：长 PV 的拖动和导出不可用；一旦为了性能跳步，预览与成片运动不一致。
- **对应设计**：§5.4 固定步长；§7.4 预览；§9 导出。
- **优先级**：P1
- **重复**：无。#17 只要求截图，不涉及解算缓存。

### A9. 改一次工程帧率，已有物理轨迹和视频源帧全部变味

- **现象/触发**：解算步长是 `1/fps`，视频/音频的 `sourceIn` 又是“素材内的第几帧”。工程设置允许改 fps，但求解段只存版本不存 fps，素材时长也按帧记录。
- **期望**：改 fps 前警告并说明影响；要么锁定已有内容的 fps，要么按时间重算 sourceIn / 重新解算，并把 fps 写进求解段版本。
- **影响**：整片速度、重力手感、视频播放速度一起变；用户确认过的预览和导出结果对不上。
- **对应设计**：§2.1 fps；§5.4 固定步长；§6.3 sourceIn。
- **优先级**：P1
- **重复**：无。

### A10. 一个物体不能同时下落和自转，常见运动做不出来

- **现象/触发**：设计规定一个求解段只能装一个效果，且段不能重叠。但重力和黑洞只驱动 x/y，自转只驱动 rotation，二者在属性上完全正交。“抛出后一边下落一边旋转”“一边公转一边自转”都无法直接表达。
- **期望**：允许驱动不同属性的段重叠，或提供“重力+自转”“公转+自转”的组合段；至少要说明用户应如何分轨表达。
- **影响**：最常见的物理表演做不出来；用户只能拆成两段，但第二段开始时第一段已经停止，运动不连续。
- **对应设计**：§5.4 一段一效果 / 不能重叠；§10 不做烘焙。
- **优先级**：P1
- **重复**：无。

### A11. 物理参数极端或退化时，物体可能消失或飞出画面

- **现象/触发**：公转起点正好在中心（半径 0）、周期填 0、扁率填 0、黑洞软化半径填 0、质量或模拟速度极大、摩擦/弹性超出合理范围。设计没有统一的参数范围、有限值检查和失败回退。
- **期望**：创建/更新时校验范围；解算每帧检查 NaN/Inf；失败时冻结在最后一个有效位姿并返回结构化错误，而不是把坏值写进画面。
- **影响**：物体瞬移、消失或飞到无穷远；工程数据看起来仍然合法，打开/导出才发现坏。
- **对应设计**：§5.4 各效果参数；§11 数值实现待细化。
- **优先级**：P1
- **重复**：无。

## B. 公转

### B1. 公转中心一动，绕行的物体就瞬移

- **现象/触发**：设计说“每帧取目标实体当前位置和旋转”。目标被关键帧移动时，椭圆中心跟着平移，绕行物体的世界位置会在同一帧整体跳一个 delta；目标旋转时，椭圆朝向和物体在椭圆上的角度也会瞬间转过去。
- **期望**：明确公转是“以开始帧中心为固定点”，还是“跟随目标平滑移动”；如果是后者，需要定义相位连续和速度传递，不能逐帧硬套新中心。
- **影响**：绕一个会动的星球运行时，卫星像在瞬移；AI 无法预测轨迹。
- **对应设计**：§5.4 公转“每帧取当前位置和旋转”。
- **优先级**：P1
- **重复**：无。

### B2. 两个物体互相公转会让预览/导出无限递归

- **现象/触发**：A 公转 B，B 又公转 A；或 A→B→C→A 的多级依赖。求值 A 的位姿要读 B，读 B 又要读 A。设计只写了一句“检测循环依赖”，没有说检测范围、检测时机和错误形态。
- **期望**：建立跨实体的求解依赖图，在 create/update 时拒绝成环并列出环路；打开工程时也校验，不能等到渲染才递归。
- **影响**：预览/导出卡死或栈溢出，严重时工程一打开就崩。
- **对应设计**：§5.4 公转“检测循环依赖”；§7.3 批量创建。
- **优先级**：P0
- **重复**：无。

### B3. 公转目标在别的父级或被缩放旋转后，椭圆画错位置

- **现象/触发**：实体的 x/y 是父级局部坐标，公转目标可能在另一个父级下，还带旋转和非均匀缩放。椭圆中心、长短轴、旋转角到底在目标局部、实体局部还是世界坐标里算，没有定义；跨父级要乘逆矩阵，非均匀缩放还会把圆压成另一个椭圆。
- **期望**：明确求解空间（世界/目标局部/实体局部），给出跨父级转换；只读 a/b 用世界单位显示；目标缩放旋转时轨迹要可预测。
- **影响**：椭圆位置和朝向整体偏掉；用户调好的参数换一个父级就变样。
- **对应设计**：§3.5 局部坐标；§5.4 公转中心与椭圆。
- **优先级**：P1
- **重复**：无。

### B4. 公转周期填 0、方向填错、起点在中心时没有报错

- **现象/触发**：`periodFrames` 为 0 或负数会除零；`direction` 不是 +1/-1 时方向未定义；`aspect` 为 0 或大于 1 时椭圆退化；起点与中心重合时半径反解为 0，物体原地不动。
- **期望**：参数范围校验并给出明确错误；起点等于中心时提示“无法确定椭圆”，而不是静默生成零半径轨道。
- **影响**：物体不动或位置变 NaN；AI 以为创建成功。
- **对应设计**：§5.4 公转参数。
- **优先级**：P2
- **重复**：与 A11 的通用数值兜底相关，但公转特有参数未被覆盖。

## C. 重力

### C1. 重力方向说的“目标实体”不明确，物体一转重力也跟着转

- **现象/触发**：设计写“方向是目标实体的局部下方（局部 +Y）；目标旋转时重力跟着转”。如果“目标实体”就是下落物体自己，那么给物体打 rotation 关键帧会让重力方向一起旋转，物体会斜着掉；如果指另一个实体，又没有字段指定这个“重力源”。
- **期望**：明确重力方向是世界向下、某个指定实体的局部向下，还是下落物体自身的局部向下；如果是后者，要说明旋转对重力的影响。
- **影响**：同一个参数在不同理解下运动完全不同；用户打旋转关键帧会得到意外轨迹。
- **对应设计**：§5.4 重力方向。
- **优先级**：P1
- **重复**：无。

### C2. 高速下落会直接穿过薄平台

- **现象/触发**：固定步长 `1/fps`，只在采样位置做碰撞检测，没有子步或连续碰撞。下落速度大、平台薄、或者平台每帧开关时，物体一步跨过平台，之后不再修正。
- **期望**：按位移/平台厚度自动子步，或做扫掠碰撞；至少检测“这一步跨过了表面”并回退到接触点。
- **影响**：导出里物体穿过地板掉出画面；低速测试正常，实际成片坏。
- **对应设计**：§5.4 碰撞；§9 导出。
- **优先级**：P1
- **重复**：无。

### C3. 物体落地后一直抖，或者停在半空

- **现象/触发**：每一步都加重力，碰撞后按弹性反弹，只有速度低于停止阈值才归零。阈值太低会永远微跳；阈值太高会在还有明显速度时突然停住，甚至停在空中。设计没有休眠、接触保持或斜坡摩擦规则。
- **期望**：连续低速接触若干帧后进入休眠；停止阈值带单位说明；斜坡上的静摩擦和滑动要分开。
- **影响**：成片里物体持续抖动；或者看起来“粘”在半空，物理感全错。
- **对应设计**：§5.4 弹性/摩擦/停止阈值。
- **优先级**：P1
- **重复**：无。

### C4. 旋转后的图片/文字，碰撞盒到底是方的还是斜的没定义

- **现象/触发**：设计说矢量用实际路径，图片/文字/HTML 用包围盒。但没说是世界轴对齐盒（AABB）还是随实体旋转的有向盒（OBB），也没说文字盒是否包含描边、内边距、竖排溢出。
- **期望**：明确使用实体局部包围盒变换到世界后的有向盒；文字/图片的盒包含哪些视觉元素要写清；预览里能显示碰撞形状。
- **影响**：旋转的长条平台会撞到“看不见的空气”；文字描边会莫名其妙挡住物体。
- **对应设计**：§5.4 碰撞形状。
- **优先级**：P1
- **重复**：无。

### C5. 每帧开关碰撞的平台会让物体瞬移或夹住

- **现象/触发**：`physicsInteract` 可关键帧。平台在物体已经重叠时从 0 切到 1，第一次碰撞会把物体推出表面（瞬移）或直接反弹；从 1 切到 0 时物体立刻下落；每帧开关就每帧抖。设计也没说实体在自身 `[start,end)` 外或被隐藏时是否还参与碰撞，以及移动平台会不会把速度传给物体。
- **期望**：定义碰撞激活条件（在范围内、可见、`physicsInteract=1`）；开启时若已重叠，温和分离而不是瞬移；移动平台按相对速度传递切向运动。
- **影响**：用关键帧做升降平台/传送带时，物体被弹飞或卡住；隐藏的平台仍然挡路。
- **对应设计**：§3.2 physicsInteract；§5.4 碰撞。
- **优先级**：P1
- **重复**：无。

## D. 黑洞

### D1. 黑洞模拟速度/质量调大后，物体可能数值爆炸或瞬移

- **现象/触发**：`simulationSpeed` 放大有效步长，质量极大或软化半径趋近 0 时中心引力趋于无穷；`maxSpeed` 只在积分后钳速度，位置已经跳出去了。没有 NaN/Inf 检查，也没有失败回退。
- **期望**：参数范围校验、按模拟速度自动子步、每帧有限值检查；超限时冻结在最后有效位姿并返回错误；明确 `maxSpeed` 是钳速度还是钳位移。
- **影响**：物体一瞬间飞出画面或变成 NaN 消失；工程数据仍合法，只有播放时才坏。
- **对应设计**：§5.4 黑洞参数；§11 数值实现待细化。
- **优先级**：P1
- **重复**：无。

### D2. 物体穿过事件视界后还完整显示，看不出是被吞了还是逃了

- **现象/触发**：设计明确“视界不是硬边界，可以穿过继续飞”，且黑洞只改 x/y，不改大小、rotation、可见性。物体进入视界后仍然完整画在黑洞上面；也没有“已逃逸/已捕获”的状态或速度、距离读数。
- **期望**：至少定义视界内外的渲染关系（被遮住/变暗/可选隐藏）；给 AI 和用户提供每帧速度、距离、是否逃逸的诊断。
- **影响**：画面看起来像物体穿模；AI 无法判断参数调对没有，只能靠人看。
- **对应设计**：§5.4 事件视界 / 只改 x/y。
- **优先级**：P2
- **重复**：无。

## E. Gizmo

### E1. 负 scale 后四角手柄会认错角，拖着拖着又翻回去

- **现象/触发**：Office 角缩放允许拖过对角顶点进入负 scale。翻转后，视觉上的左上角其实是原来的右下角；如果手柄仍按局部角 ID 绑定，下一次拖动会锚错对角顶点，对象跳一下或立刻翻回正 scale。
- **期望**：手柄绑定视觉角而不是局部角；翻转后对角锚点仍是视觉对角；从正到负、负到正连续拖动不跳变；单测覆盖翻转后的再次缩放。
- **影响**：用户无法可靠地翻转并继续调整图片/摄像机；每次翻转后都要重新选。
- **对应设计**：§3.6 Office 角缩放 / 负 scale；§3.5 pivot。
- **优先级**：P1
- **重复**：相关 #9（四角手柄不跟鼠标）和 #19（pivot 语义），但“负 scale 后手柄身份与锚点互换”未被覆盖。

### E2. 中心缩放手柄拖过轴心时，物体会消失或方向乱跳

- **现象/触发**：中心方块在轴心局部 +X/+Y 方向。拖过轴心时 scale 经过 0，矩阵奇异，画面直接消失；继续拖进入负值，象限与翻转的对应关系、斜向拖动到底改 X 还是 Y，都没有定义。
- **期望**：零点附近有死区/最小绝对值；明确斜向拖动的主轴判定；负 scale 下按视觉象限决定翻转；Shift 等比时保持符号。
- **影响**：用户拖到一半物体不见了，松手后又从另一边出现；无法精确控制翻转。
- **对应设计**：§3.6 中心缩放 / 四象限翻转。
- **优先级**：P1
- **重复**：无。

### E3. 父级旋转/非均匀缩放后，gizmo 手柄不在看到的轴上

- **现象/触发**：设计说 X/Y 轴跟随实体 rotation，是局部坐标轴；但 gizmo 的输入只有实体自身变换、包围盒和视图缩放，没有父级世界矩阵。父级旋转或非均匀缩放后，屏幕上的视觉轴和实体局部轴不一致，手柄会偏。
- **期望**：gizmo 接收完整父级世界变换；手柄画在最终视觉轴上；角缩放的对角锚点也在世界空间里保持不动。
- **影响**：拖 X 轴物体斜着走；角缩放锚点漂移；嵌套层级越深越明显。
- **对应设计**：§3.5 父子变换；§3.6 Gizmo；实现合同的 gizmo 接口。
- **优先级**：P1
- **重复**：相关 #19，但“父级变换未进入 gizmo 接口”是新的接口缺口。

### E4. 四角旋转、缩放、中心方块挤在一起时总是抓错

- **现象/触发**：四个角外侧是旋转双箭头，内侧是方形缩放手柄，轴心附近还有中心方块和移动箭头。小实体、缩小视图或负 scale 时，这些命中区会重叠；设计没有命中优先级和最小屏幕尺寸。
- **期望**：固定优先级（例如旋转 > 角缩放 > 中心缩放 > 移动），每个手柄有最小可点击尺寸，拥挤时隐藏低优先级手柄，鼠标悬停显示光标。
- **影响**：想旋转却缩放，想缩放却移动；松开鼠标就提交一个错误操作。
- **对应设计**：§3.6 手柄布局；§11 命中范围待细化。
- **优先级**：P1
- **重复**：无。

### E5. 旋转时按 Alt 换轴心会跳，Linux 下还可能拖动整个窗口

- **现象/触发**：默认绕 pivot 旋转，按住 Alt 临时改绕包围盒中心。拖动中途按下/松开 Alt 会换旋转中心，如果不做补偿，对象会跳一下；在 Linux 桌面，Alt+拖动常被窗口管理器占用为移动窗口。
- **期望**：轴心切换只在拖动开始时生效，或切换时补偿当前角度；提供快捷键重映射；文档说明桌面环境冲突。
- **影响**：精细旋转做不了；用户以为在转对象，结果整个窗口被拖走。
- **对应设计**：§3.6 旋转 Alt。
- **优先级**：P2
- **重复**：无。

### E6. 摄像机负 scale 拖过 0 会跳变，导出是否镜像也没说清

- **现象/触发**：摄像机 scale 的绝对值被限制在 0.05..1，又允许负值。拖过 0 时会被钳到 ±0.05，画面突然跳一下；负 scale 到底只是取景框翻转，还是最终导出画面也镜像，设计没有定义。
- **期望**：零点附近有连续过渡/死区；明确负 scale 对预览和导出的影响；摄像机框上显示当前朝向。
- **影响**：调摄像机时画面突然放大/翻转；导出成片方向和人看到的不一致。
- **对应设计**：§3.3 摄像机参数；§3.6 负 scale。
- **优先级**：P2
- **重复**：无。

## F. 时间轴

### F1. 删掉几行后，新片段会跑到很高的空行

- **现象/触发**：行号持久化，删除实体不压缩其他行；新实体默认放在“范围内已占用最高 row + 1”。反复增删后，可能只剩一个实体却占着 row 999，下一个新实体直接落到 row 1000，时间轴上方出现大片空白。
- **期望**：在范围内优先复用最低空闲 row，或提供“压缩行”操作；至少不要让新实体落到视野外。
- **影响**：时间轴越用越空、越用越长；用户找不到刚创建的片段。
- **对应设计**：§4 新实体默认 row / 行号持久化；§3.5 row 排序。
- **优先级**：P1
- **重复**：无。

### F2. 时间轴无限长，但没人知道“工程结尾”在哪

- **现象/触发**：设计只说水平方向无限、导出范围由摄像机决定，没有定义内容结尾。播放范围、适应窗口、滚动条长度、“跳到结尾”、MCP 返回的时长都没有基准；空工程时更无从判断。
- **期望**：用“所有实体 end 与摄像机 end 的最大值”定义内容结尾并显示结束标记；适应窗口以它为范围；滚动条不随无限画布无限延长。
- **影响**：用户无法判断工程多长；缩放到全片没有依据；AI 也不知道该把播放头放到哪。
- **对应设计**：§4 无限长；§9 导出范围。
- **优先级**：P1
- **重复**：相关 #8（最小缩放看不完整篇），但新模型把时间轴改成无限后，“结尾”本身没有定义，问题更根本。

### F3. 私有时间线可以一层层打开，但快捷键和焦点不知道属于哪层

- **现象/触发**：任意实体都能当父级，双击打开私有时间线浮层；子级还能再开一层。多层浮层叠在一起时，Del、Ctrl+Z、框选到底作用于哪一层没有定义；MCP 的视图状态只返回一个 owner UUID。
- **期望**：明确“同一时间只有一个活动时间线”；提供面包屑和 Esc 逐层返回；快捷键按活动层作用；MCP 能读到完整层级路径。
- **影响**：用户在浮层里按删除，删掉的可能是主时间线的选中项；AI 也判断不了人类正在编辑哪一层。
- **对应设计**：§3.4 私有时间线；§4 浮层；§7.4 view.state。
- **优先级**：P1
- **重复**：相关 #4（浮层空内容过高），但本条是嵌套层级与焦点归属，不是布局。

### F4. 物理段的颜色带能不能点、能不能拖没说清

- **现象/触发**：求解段用专门颜色带标出，开始/结束用不同标记，被驱动轨道在段内锁定。但颜色带是否可选、可拖动、可裁剪、可删除，和普通 clip 的裁剪手柄谁优先，都没有定义。
- **期望**：颜色带是可点击的只读覆盖层，点击选中段并在右侧面板编辑；裁剪仍由 clip 手柄负责；锁定轨道有明确的锁图标和原因提示。
- **影响**：用户不知道该怎么修改或删除一个物理段；误拖 clip 边缘又触发 A1 的整段失效。
- **对应设计**：§5.4 时间轴显示；§4 时间轴交互。
- **优先级**：P2
- **重复**：无。

## G. 素材

### G1. 素材缺失时导出不报错，成片静默少一层

- **现象/触发**：设计只定义了编辑器里的“素材缺失”占位和 MCP 缺失列表，没有定义导出行为。缺图片、视频、音频或 HTML 时，导出可能跳过、画占位、或直接失败，三种结果都没有规定。
- **期望**：导出前做预检，列出缺失素材及受影响实体；默认阻止导出或要求显式确认“按占位导出”；音频缺失不能静默变无声。
- **影响**：成片少图层/少声音，用户上传后才发现；AI 也无法判断导出是否完整。
- **对应设计**：§6.1 缺失素材；§9 导出。
- **优先级**：P1
- **重复**：无。#5 是素材库删除入口，不是导出行为。

### G2. 每段视频都拆一份无损 WAV，工程仓库很快膨胀

- **现象/触发**：导入视频自动拆出完整 WAV，48kHz 立体声 24bit 约 0.6–1GB/小时，且和视频一起进 Git LFS。设计没有压缩格式、代理音频、体积预估或“只要视频不要原声”的选项。
- **期望**：内部可用 FLAC/AAC 等无损或高质量压缩；导入时显示预计体积；允许只保留视频或只保留音频；同一内容按哈希复用。
- **影响**：长视频工程的仓库迅速到几十 GB，clone/push 和 LFS 配额都撑不住。
- **对应设计**：§6.3 视频拆 WAV；§8.1 Git LFS。
- **优先级**：P1
- **重复**：无。

### G3. 导入 .pvhtml zip 时没有防路径穿越和解压炸弹

- **现象/触发**：设计说支持 zip 自动解包，只要求校验 `index.html`。没有规定 `../`、绝对路径、符号链接、超大解压体积、文件数上限，也没有规定 zip 里只有一个顶层目录时是否自动剥掉。
- **期望**：解压到临时目录并拒绝越界路径/符号链接；限制体积和文件数；自动处理单顶层目录；失败时不留下半个 bundle。
- **影响**：恶意或误制的 zip 可能写到工程目录外；正常打包的 zip 又因为多一层目录而导入失败。
- **对应设计**：§6.4 .pvhtml 目录包 / zip。
- **优先级**：P1
- **重复**：无。#16 是 MCP 创建 HTML 层，不是 zip 解包安全。

### G4. 同一个 .pvhtml 换台机器就变成新素材，重新编码的素材也找不回来

- **现象/触发**：目录包整体算一个 sha256，但没规定哈希是否包含文件顺序、权限、mtime、符号链接和路径分隔符；同一份包在不同机器上可能算出不同哈希。另一头，素材重新导出/转码后字节变了，哈希必然不同，自动恢复只认原哈希，用户没有“按名字找候选并重新链接”的入口。
- **期望**：目录哈希只基于排序后的相对路径和文件内容，跨平台稳定；缺失素材提供候选列表（按原文件名/类型/尺寸）和“重新链接”，MCP 也能执行。
- **影响**：去重失效、仓库里出现重复包；换机器后旧引用恢复不了，只能逐个手动替换。
- **对应设计**：§6.1 sha256 去重 / 重新导入恢复；§6.4 目录包。
- **优先级**：P2
- **重复**：无。

### G5. 找不到 Chrome 时预览有占位，导出却可能静默缺层或卡住

- **现象/触发**：设计只说找不到 Chrome 时 HTML 层显示错误占位，其他功能不受影响；没有说导出时怎么办，也没有 Chrome 版本探测、单帧超时、崩溃重试。按帧截图时一个页面卡住，整个导出就停在那里。
- **期望**：启动时探测 Chrome 并显示版本；导出前预检，缺 Chrome 直接报错而不是输出占位；每帧有超时和重试，失败时明确标记是哪一层哪一帧。
- **影响**：成片里 HTML 层整段消失，或者导出无限等待；用户以为只是预览问题。
- **对应设计**：§6.4 外部无头 Chrome；§9 导出。
- **优先级**：P1
- **重复**：无。

### G6. HTML 在预览尺寸和导出尺寸下排版不同，AI 看到的不是成片

- **现象/触发**：截图缓存键包含输出尺寸，说明预览和导出可能用不同分辨率。如果 bundle 里有响应式 CSS、百分比布局或媒体查询，预览尺寸下的排版会和 1920×1080 导出不同；AI 通过预览截图确认的构图，成片里会变。
- **期望**：HTML 始终按 manifest 的逻辑尺寸渲染再缩放，或明确规定“预览按导出尺寸渲染”；文档说明响应式布局的风险。
- **影响**：AI 和用户都以为画面没问题，导出后文字换行、元素错位。
- **对应设计**：§6.4 缓存键 / 输出尺寸；§7.4 预览。
- **优先级**：P1
- **重复**：无。

### G7. 换一个更短的素材会自动裁短片段并删关键帧，没有确认

- **现象/触发**：设计规定换素材时如果新素材更短，实体 end 自动裁到 `start + 新素材时长`，越界关键帧删除；换回长素材也不恢复。整个过程没有确认或预览。
- **期望**：换素材前显示“会裁掉多少帧、删除多少关键帧”，要求确认；或者先保留数据、只做渲染裁剪，等用户主动清理。
- **影响**：误换一个短素材就永久丢掉后半段动画；undo 能救，但用户往往先看到画面变了。
- **对应设计**：§6.2 换素材 / 时长裁短。
- **优先级**：P1
- **重复**：无。

## H. Git

### H1. 一次 commit 失败后，下一次操作会把两次改动一起提交

- **现象/触发**：设计说 commit 失败要报告错误、保留文件、允许重试。但应用继续可用；用户或 AI 接着做下一个操作，下一次 commit 会把上一次没提交的改动一起带上，提交消息只描述第二次操作。
- **期望**：commit 失败后进入“待提交/只读”状态，阻止新写操作直到重试成功；或者把失败操作排队，用原消息补提交。
- **影响**：一次 undo 会回退两个操作；“一次操作一个 commit”的承诺失效，历史面板和 AI 的 history.log 都不可信。
- **对应设计**：§8.2 提交粒度 / commit 失败。
- **优先级**：P1
- **重复**：无。

### H2. 手动改过的实体文件会被应用静默覆盖

- **现象/触发**：应用只提交自己写过的路径，也不监听文件变化。用户或外部工具手动改了某个实体 JSON 后，应用内存里还是旧数据；下一次保存会整文件覆盖，手动改动丢失。改的是其他文件时，又永远不会被纳入提交。
- **期望**：写入前检查文件 mtime/内容哈希，发现外部修改就提示“重新加载/覆盖/另存”；或者监听工程目录并自动刷新。
- **影响**：手工修数据、外部脚本生成的内容会被无声抹掉；git 状态和应用内状态长期不一致。
- **对应设计**：§8.2 只提交本应用路径；§7.1 文件格式不作为 AI 写接口。
- **优先级**：P1
- **重复**：无。

### H3. Ctrl+Z 遇到根提交、手动改动或连续回退就会冲突

- **现象/触发**：Ctrl+Z 用 `git revert` 最近一个操作 commit。第一次提交没有父提交，revert 会失败；用户手动改过同一文件时 revert 会冲突并把冲突标记写进实体 JSON；连续回退多个提交可能互相冲突；LFS 指针恢复也可能失败。
- **期望**：定义清晰的失败与恢复流程：根提交禁用 undo；冲突时 `revert --abort` 并解释，不把冲突标记留在工程文件里；历史面板回退前先检查工作区是否干净。
- **影响**：最需要撤销的时候 Ctrl+Z 不可用；工程被冲突标记弄成无法解析的 JSON。
- **对应设计**：§8.3 撤销 / revert。
- **优先级**：P1
- **重复**：无。

### H4. MCP 和人类同时写工程会互相覆盖，还会撞上 git 锁

- **现象/触发**：MCP 可能并行收到多个工具调用，人类同时在拖动/输入；两边都读旧状态、整文件写入、各自 `git add/commit`。结果可能是 `index.lock` 报错、两次操作的改动混进同一个 commit，或者后写的整文件覆盖先写的。
- **期望**：UI 和 MCP 共用一条写队列/工程级互斥锁；实体写入带 revision 或 mtime 的乐观并发检查；git 操作串行化，忙时返回可重试错误。
- **影响**：提交缺失或混合，undo 回退错操作；人和 AI 都以为自己的修改生效了，实际被覆盖。
- **对应设计**：§8.2 一次调用一个 commit；§7.1 MCP 全工程可写。
- **优先级**：P0
- **重复**：无。

### H5. 克隆工程没拉 LFS 时，素材指针会被当成真素材

- **现象/触发**：`git-lfs` 是硬依赖，但“安装了 git-lfs”不等于“已经 `git lfs pull`”。克隆下来的素材文件可能只是几十字节的指针文本；应用按内容算哈希会得到错误值，按图片解码会失败，甚至把指针当成素材导入。
- **期望**：打开工程时检测 LFS 指针文件并提示 `git lfs pull`；不要用指针内容计算素材哈希；素材校验失败时显示缺失而不是损坏。
- **影响**：工程看起来“素材全坏”，用户重新导入后产生重复素材；AI 读到错误的素材列表。
- **对应设计**：§8.1 git-lfs 硬依赖；§6.1 素材哈希。
- **优先级**：P1
- **重复**：无。

### H6. 每次鼠标释放都 commit，历史爆炸且崩溃会丢整段拖拽

- **现象/触发**：一次拖拽、一次输入框失焦、一次按钮点击都生成一个 commit。大量微调会产生成百上千个提交，历史面板和 git 操作变慢。反过来，长拖拽过程中应用崩溃，因为还没到“鼠标释放”，这段修改完全没有落盘。
- **期望**：对同一实体的连续微调做时间窗合并（仍保持一次 undo 回退一个逻辑操作）；拖拽过程中定期写草稿，崩溃后可恢复。
- **影响**：工程历史臃肿、面板卡顿；崩溃丢几分钟工作。
- **对应设计**：§8.2 提交粒度。
- **优先级**：P2
- **重复**：无。

## I. MCP

### I1. 危险操作的 confirm 只是 AI 自己填的参数，没有人真正确认

- **现象/触发**：删除父级、批量删除、删除素材要求 `confirm: true`。但 AI 可以自己把 `true` 填上，没有人类批准、影响面预览或二次令牌。级联删除可能带走几十个后代和引用。
- **期望**：危险操作先返回影响面（实体数、后代数、被引用素材数），需要人类在 UI 确认或使用一次性令牌；至少不要用“AI 自己能填的布尔值”当安全门。
- **影响**：AI 一次误判就能删掉整棵子树；虽然可以 git 回退，但现场已被打断。
- **对应设计**：§7.1 危险操作 confirm。
- **优先级**：P1
- **重复**：无。

### I2. MCP 只能导入本地路径，远程 AI 没法把素材带进工程

- **现象/触发**：`asset.import` 接收“本地路径 -> 复制进工程”。如果 AI 不在用户机器上运行，或者素材来自对话/生成结果，它没有可访问的本地路径，也没有字节上传或 URL 拉取接口。
- **期望**：支持上传字节/分块、或先写入工程内 staging 目录再导入；明确远程 AI 的标准工作流；对 URL 导入做安全限制。
- **影响**：AI 无法独立完成“找素材→建工程→排版”的闭环，只能让人类手动导入。
- **对应设计**：§7.2 asset.import；§6.1 素材存储。
- **优先级**：P1
- **重复**：相关 #16（MCP 不能创建 HTML 层，提到文件路径被拒），但本条是所有素材的导入通道，范围更大。

### I3. schema 和 guide 还是手写的，迟早又和实现不一致

- **现象/触发**：新模型提供 `schema.get` / `guide.get`，但内容来源没有约束；文档 agent 另写一份工具说明，运行时工具注册又是第三处。旧模型已经出现过指南说只读、schema 版本落后、列出不存在工具的问题。
- **期望**：schema 从工具注册描述自动生成，guide 示例由同一份 schema 驱动；CI 校验每个工具/参数都在文档里，版本号随工程格式走。
- **影响**：AI 按文档传参被拒，或者传了“成功但无效”的参数；问题会随着工具增加反复出现。
- **对应设计**：§7.2 schema.get / guide.get；§11 工具 schema 待细化。
- **优先级**：P1
- **重复**：相关 #29（旧指南/schema 漂移），但本条是新模型的 schema 来源与防漂移机制，不是重复旧内容。

### I4. 批量工具说全回滚，但进程中断会留下半个工程

- **现象/触发**：`createTree`、`updateMany`、`deleteMany`、`setMany` 要求“要么全部成功，要么整次回滚”。实现要跨多个实体文件甚至素材目录写入；如果写到一半进程崩溃、磁盘满、或回滚本身失败，工程会停在半完成状态。
- **期望**：先全量校验，再写临时目录/临时文件，最后原子替换；启动时能检测并恢复未完成事务；回滚失败要保留日志和可恢复入口。
- **影响**：工程半新半旧，打开校验失败；AI 以为批量成功，实际只写了一半。
- **对应设计**：§7.3 批量工具全回滚。
- **优先级**：P1
- **重复**：无。

### I5. AI 调 undo 可能撤销的是人类刚做的操作

- **现象/触发**：`history.undo` 回退“最近一个操作 commit”，但提交不区分操作者。AI 想撤销自己上一步，如果人类在此期间点了一下、拖了一下，回退掉的是人类的工作。
- **期望**：提交记录带操作者/会话标签；`history.undo` 支持按 commit id 或“撤销我这个会话的最近一次”；人类操作被 AI 回退前要确认。
- **影响**：AI 静默破坏人类刚做的修改，且人类很难理解为什么画面退回去了。
- **对应设计**：§8.3 撤销；§7.2 history.undo。
- **优先级**：P1
- **重复**：无。

### I6. 锁定实体在级联删除/父级移动/批量写入时到底算不算写，没有定义

- **现象/触发**：MCP 遵守 `locked`，写锁定实体返回错误。但删除父级会级联删除锁定的子级；移动父级会同步平移锁定子级的 start/end；批量工具里混入一个锁定实体；求解段可能驱动锁定实体的 x/y。这些路径算不算“写锁定实体”，设计没有说。
- **期望**：逐条定义：级联删除遇到锁定子级是阻止整个操作、跳过并报错、还是允许；父级移动是否允许带动锁定子级；批量操作必须全回滚；锁定实体上的求解段是否还能预览。
- **影响**：同一把锁在不同操作下表现不一致；用户以为锁住了，父级一拖还是被改。
- **对应设计**：§3.2 locked；§3.4 级联删除/父级移动；§7.1 MCP 遵守 locked。
- **优先级**：P1
- **重复**：相关 #25（旧 UI 没有锁定入口）、#35（旧 clip 锁定仍可拖），但本条是新模型级联路径的锁语义，不是 UI 入口。

## J. 跨模型

### J1. 换父级既能造出父子环，也能把子实体放到父范围外

- **现象/触发**：`entity.reparent` 只讨论“保持世界位置/保持局部坐标”，没有说不能把父级换到自己的后代下面，也没有说子实体 `[start,end)` 超出新父级范围时是裁剪、拒绝还是静默丢弃。父子环会让扫描/渲染/选择递归到栈溢出；范围超界会产生“私有时间线看不见、预览还在画”的旧问题。
- **期望**：换父级前做完整预检：拒绝成环并列出路径；范围超出时提供“裁到父范围”或“拒绝”两种明确选择，不静默改数据；MCP 返回结构化原因。
- **影响**：一次换父级就可能让工程打不开；或者悄悄删掉子实体的关键帧和后代。
- **对应设计**：§3.4 换父级 / 子实体范围；§2 按 parentUuid 组树。
- **优先级**：P0
- **重复**：无。
